# 上游更新的共用审查约定

本文只规定**审查如何做**，不规定源码如何暂存、复制、补丁如何重放或产物如何构建。每个上游项目的专用手册负责这些执行细节。开始一次更新时，阅读本文和对应项目的手册；不需要阅读其他项目的同步手册。

## 更新范围

以最后一次完成接入的提交为起点，以本次解析出的完整 commit SHA 为终点。先保留旧 pin，使用隔离的工作树准备候选结果。不要把移动分支名、成功复制源码或通过静态一致性检查当成更新完成。

## 变更清单和分类

先检查起点到终点的**完整上游差异**，不只看最终会复制进来的源码闭包。按路径列出变化，并按功能归组。测试、文档、发布脚本、部署配置和其它平台目录都进入清单，避免它们引入的行为或默认值被漏掉。

清单完成后按与产品的关系分层：

- **深入审查**：当前产品会编译、复制、调用或由用户配置到的源码、生成配方、部署设置，以及可能改变默认行为、接口、数据/资源布局或消费者可达性的改动。
- **作为证据阅读**：测试和文档。它们用来解释新行为、作者声称修复的问题、默认值及验收条件；只有影响接入判断时才深入阅读，不要求逐个测试文件或逐段文档做长篇审阅。
- **排除或暂缓**：产品不使用的平台、工具或功能。记录路径或功能组，以及具体排除原因；若暂缓的是有产品消费者的功能，再写清依赖、后续步骤和验收条件。

不要因为文件名带有 `test`、`experimental`、`benchmark` 或 `diagnostic` 就自动排除或接入。若生成器、部署配置或实验开关会影响实际生产构建/调用路径，应按生产变更追踪。

## 按功能追踪和决定

每个相关功能组至少回答：

1. 改了什么行为、接口、默认值、资源布局或生成方式？
2. 本产品是否包含它？从配置/宿主到 runtime、模块或着色器的实际消费者链在哪里？
3. 本地是否已有适配、补丁或不同默认值？新版本会覆盖、重复实现或改变这些行为吗？
4. 选择接入、暂缓还是排除，依据是什么？需要哪些验证才能支持这个决定？

检查开关时根据消费者和执行路径判断，不能仅凭名字决定；尤其留意默认值变化、数值或枚举含义变化、参数删除、接口/布局变化，以及生成脚本与提交产物之间的不一致。不需要逐个追踪中间提交；最终差异无法解释行为或回归来源时，再查相关历史。

审阅记录使用该项目自己的格式，但结论应能追到具体功能、路径或源码位置，并包含理由和证据。接入项写实际验证命令和结果；暂缓项写明确的后续步骤及验收条件；排除项写产品不消费它的依据。不得批量填充模板来制造审阅通过。

## 完成边界

源码准备、补丁回放、静态一致性检查和编译分别只证明各自覆盖的部分。按风险完成对应的 ABI、资源/队列顺序、模块/着色器、画面或游戏验证，并记录未做的验证。验证完成后才更新该项目的完成 pin；若项目手册有 pending 状态，失败或暂缓期间应保留 pending，不能伪装成已接入。

编译成功不代表游戏验收、性能收益或所有设备兼容；没有运行过的项目应明确标为未验证。
